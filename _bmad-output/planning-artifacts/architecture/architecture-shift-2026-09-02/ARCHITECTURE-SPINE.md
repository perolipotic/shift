# Architecture Spine — Shift

## Design Paradigm

**The database stores only what a human asserted; everything else is a pure function of it.**

Three kinds of row exist, and nothing else does:

| Kind | Contents |
| --- | --- |
| **Rules** | organization settings, hour bands, shift types, teams, members, allowances, rotation patterns and steps, rotation assignments |
| **Exceptions** | shift-type overrides, roster overrides, leave records |
| **Decisions** | conflict resolutions, each with its attribution |

Everything a user reads is derived from those: the projected schedule, shift rosters, band hours, total hours, leave-day counts, leave balances, leave/schedule collisions, and coverage and rest-gap warnings.

The derivation lives in one pure package that cannot reach for data. The store enforces who may assert what. There is nothing in between.

## Invariants & Rules

### AD-1 — Nothing derived is ever persisted

- **Binds:** all; CAP-11, CAP-13, CAP-14, CAP-15, CAP-16
- **Prevents:** one unit reading a materialized row while another recomputes, and the two disagreeing — the drift that makes DI-1 and DI-2 unverifiable.
- **Rule:** No table may hold a value the domain package can compute. Adding a column that caches a derived figure requires amending this AD, not a migration.

- **Amended 2026-11-21 (Architect pass 1) — the scope note.** Derivation may also run on the server, inside the `calendar-feed` and `remind` Edge Functions (AD-14), using the same domain package (AD-7) over one assembly of asserted rows (AD-19). Nothing derived is persisted for it: not in a table, not in a cache, not in a worker's memory across requests. Those two functions write only `calendar_feed_tokens.last_fetched_at`, an attribution instant, and `notification_outbox` rows, codes and operands under AD-18's one exception. The rule itself is unchanged.

### AD-2 — Every rule that feeds derivation declares whether it is versioned or current-state

- **Binds:** CAP-3, CAP-4, CAP-6, CAP-8, CAP-9, CAP-11; engine-rules R1.1, R1.2, R2.10, R7.4
- **Prevents:** history silently rewriting itself. Under AD-1 there are no stored shifts, so a rule edit re-derives *every past date* through the new value by default — which quietly violates CAP-4's "alters no past shift", CAP-6's "forward only, rewrites no history", and CAP-9's "shifts before the effective date are unchanged".
- **Rule:** Retroactivity is never incidental. Each rule kind is classified below, and a versioned rule carries a validity range, is never updated in place, and is selected by the date being derived.

  | Rule | Classification | Because |
  | --- | --- | --- |
  | Rotation assignment | **Versioned** | CAP-9 — shifts before the effective date are unchanged |
  | Team membership | **Versioned** | CAP-6 — a team move changes the schedule forward only |
  | Member active status | **Versioned** | CAP-4 — deactivation removes from *future* rosters and alters no past shift |
  | Rotation pattern and steps | **Versioned** | reached through a versioned assignment; editing in place would defeat it |
  | Shift type **times** | **Versioned** | an edit would otherwise change accepted totals for closed months, and there is no period locking to catch it |
  | Shift type **name** | **Current-state** | a rename is cosmetic; versioning it would churn the hot path for a typo fix |
  | Hour bands | **Current-state** | CAP-3 explicitly *wants* retroactivity — moving a boundary recomputes reported band hours, and changes no total |
  | Leave allowance | **Versioned per leave year** | carry-over (13.4) reads last year's allowance as it was, and a past year's balance uses that year's allowance; `members.leave_allowance_days` is the starting allowance and `leave_allowances` holds append-only versions, each for one leave year (CAP-15 holds per leave year) (amended 2026-11-10, story 13.3). Amended 2026-11-10 (story 13.3b): sessions cannot update the starting allowance (`0056`), so it is written only when a member is created, and the app writes only versions |
  | Team position | **Versioned** (on the team-membership version) | a promotion takes effect from a date; the roster for a past date shows the position then held (added 2026-09-25, sprint change) |
  | Member fire rank | **Current-state** | descriptive only, like shift type name; nothing derived reads it (added 2026-09-25, sprint change) |
  | Minimum members | **Current-state** | FR-70 — changing it changes the short-staffed state of past and future shifts alike, as moving an hour band re-reports band hours; `organizations.minimum_members`, nullable, empty reports nothing (added 2026-11-04, story 11.1) |
  | Absence type | **Current-state** | like a shift type name: a rename is cosmetic, and whether a type draws down the allowance is its present setting; `absence_types` holds a name and `draws_allowance` and nothing else, no reason (Q5) (added 2026-11-08, story 13.1) |
  | Carry-over setting | **Current-state** | like minimum members: a change re-derives every balance (R4.15); four nullable columns on `organizations` (`carry_over_max_days`, `carry_over_expiry_month`, `carry_over_expiry_day`, `carry_over_first_leave_year`), all four or none, no default (DI-8) (added 2026-11-11, story 13.4) |
  | Loan | **Exception** (dated, never versioned) | like a leave record: it covers an inclusive date range, is removed rather than edited, and a past date stays covered unless the loan is removed; a removal returns every covered date to what it would be with no loan (R11.4). `team_loans` (added 2026-11-20, story 18.2) |

  A new rule kind is unclassified until it appears in this table.
- **Amended 2026-11-04 (story 11.1).** The table gains the minimum-members row, current-state, as `0048` ships it: one nullable `smallint` on `organizations` (`>= 1`), with no history and no default (DI-8). `domain/staffing` derives short-staffed shifts from it on read (R10.1–R10.5); no table stores a count or a state (AD-1).
- **Amended 2026-11-08 (story 13.1).** The table gains the absence-type row, current-state, as `0052` ships it: `absence_types`, keyed `(organization_id, id)`, a name (0024's `name_key` rules, at most 100 characters) and `draws_allowance`. Annual leave has the one fixed id `00000000-0000-0000-0000-000000000001` in every organization; it may be renamed, is never deleted, and always draws (a check). `leave_records.absence_type_id` is `not null default` that id, with a composite foreign key to `absence_types (organization_id, id)` and no trigger, so every existing record and every insert that names no type is annual leave and every figure reads as before. Every organization has annual leave: `0052` seeds the existing ones, and the AFTER INSERT row trigger `organizations_seed_absence_types` (definer `private.seed_absence_types()`, `search_path = ''`, callable by nobody) seeds each new one. It refuses nothing and computes nothing, so it is no AD-3 refusing trigger.
- **Amended 2026-11-10 (story 13.3).** The leave-allowance row changes from current-state to **versioned per leave year**, as `0055` ships it. `members.leave_allowance_days` stays as the member's STARTING allowance, which covers every leave year until a version sets another, so member creation stays one insert and nothing is backfilled. `leave_allowances` holds the versions: `organization_id` first, `id bigint generated always as identity`, `member_id` (composite key to `members (organization_id, id)`, no cascade), `leave_year smallint` (1–9999, the calendar year in which the leave year begins), `days smallint >= 0`, and AD-11 attribution. A version is APPEND-ONLY: no session holds an update or delete privilege, and a same-year correction is a new row with a higher `id`. An active admin inserts; an active admin reads the organization's versions and a member their own. RESOLUTION is `packages/domain/leave`'s alone (AD-7): the allowance of leave year Y is the highest-`id` version for Y; otherwise the highest-`id` version of the latest year before Y; otherwise the starting allowance. No leave-year arithmetic, trigger or function in SQL. The validity range of a version is its leave year, selected by the leave year being derived.
- **Amended 2026-11-10 (story 13.3b).** No session updates the starting allowance: `0056` revokes UPDATE on `members` from `authenticated` and `anon` and grants `authenticated` UPDATE on `name`, `email`, `role`, `username` and `fire_rank` only, every column a session updates (the app's member PATCH and admin-auth's caller-client username update). INSERT is unchanged, so admin-auth's create still writes `leave_allowance_days`. Any column later added to `members` that sessions must update needs its own column grant. The member page's *Promijeni pravo* appends a `leave_allowances` version for the current leave year, held when the dialog opens; setting any other year is out of scope.
- **Amended 2026-11-11 (story 13.4).** The table gains the carry-over setting row, current-state, as `0057` ships it: four nullable `smallint` columns on `organizations`, with no history and no default (DI-8), each under a named check — the cap `>= 1` (`organizations_carry_over_max_days_check`), the expiry month 1–12 (`…_expiry_month_check`), the expiry day 1 to its month's last day with February at 28 (`…_expiry_day_check`, so 30.06. fits and 31.06. and 29.02. do not), and the first leave year carried INTO, 1–9999 like `leave_allowances.leave_year` (`…_first_leave_year_check`) — and `organizations_carry_over_all_or_none`: all four null (no carry-over) or all four set. `authenticated` gains UPDATE on the four columns; who may write them is `0004`'s update policy, unchanged. Nothing is derived or stored from it in 13.4; the derivation of carried days, their expiry and the balance is `packages/domain/leave`'s on read (AD-1, AD-7), story 13.4b. The expiry in leave year Y is the first date on or after Y's first day with the stored day and month.
- **Amended 2026-11-13 (stories 13.5, 13.5b; epic 13 retro A6).** A half day is a fact of the record, not a rule, so it adds no row to the table. `leave_records.half` (`0058`) and `leave_requests.half` (`0059`) are nullable text, `FIRST` or `SECOND` of the member's working shift that date, under named checks (`…_half_check`, and `…_half_one_date`: a half only on a one-date range). Null is a whole day, so every existing row and every insert that names no half reads as before. `amend_leave_record` gains `p_half text default null`, and null amends to a whole day. `decide_leave_request` copies the request's half into the record it creates and never chooses one. Whether that date holds exactly one working shift is DERIVED (AD-1), so the database cannot check it. The client refuses a half at ENTRY: a new record, a member's request, and an amend that chooses another date or the other half. A STORED half is never refused for its shift: the request's decision, and an amend that keeps the record's own date and half (epic 13 retro A2). `packages/domain/leave` costs it on read, 0.5 on a date with exactly one working shift and 0 otherwise, and splits that shift at its nominal midpoint for hours.
- **Amended 2026-11-20 (story 18.2).** The table gains the Loan row, an **exception** like a leave record, neither versioned nor current-state, as `0062` ships it. `team_loans`: `organization_id` first; the member and the loan team, each a composite key to its own tenant's row, no cascade; `during daterange`, inclusive, bounded, non-empty, in years 0001–9999, with no length cap; a `reason` of 1–200 code points after 0036's trim (FR-88); AD-11's `created_by`/`created_at`; `removed_by`/`removed_at`, both or neither, which no session writes yet (18.4). A **live** loan has `removed_at is null`; ending a loan early is 18.4's amend, which removes the row and inserts a shorter one, so the dates already worked stay covered. Refused by shape (AD-3): two live loans of one member sharing a date (`team_loans_no_overlap`, an `EXCLUDE USING gist`, 23P01); a loan to an archived team, and a loan to the team the member is on, by their membership versions, on any covered date — both conjuncts of the insert policy (42501), decided on the statement's snapshot, so a team move written after the loan can still make it point home, which the domain derives as the home team (R11.3), and a team archived concurrently is a residual race, as for leave records. No trigger but AD-11's two. Only an active admin reads and inserts the table, which holds the reason (FR-92); every active member reads the live loans through the definer `calendar_team_loans()` — id, member, loan team, first and last date, no reason, no author — because R11.2 needs every member's loans to derive any roster a member is shown. The calendar snapshot (AD-13) reads it as a fourth rpc and carries each member's loans on their `members` entry and the viewer, so every roster, hour, conflict and staffing figure follows a loan through `packages/domain`'s one rule (`effectiveTeamOn`, AD-7). Nothing derived is stored (AD-1).
- **Amended 2026-11-21 (story 18.4).** A loan changes only through two attributed definers (`0064`), still with no update or delete grant: `remove_team_loan` soft-removes a live loan, and `amend_team_loan` soft-removes it and inserts the replacement (same member; the named team, inclusive range and reason, or the stored reason when none is named) in one transaction. Changing the dates or the team and ending a loan early are all that amend. Both take 0023's organization lock first and re-read the caller (42501); a loan not live is P0002 `TEAM_LOAN_NOT_LIVE`. The amend writes as the owner, past the insert policy, so 0062's two team conjuncts (archived, or the member's team on a covered date) are stated once more as `private.team_loan_team_refused`, which the amend asks (42501 `TEAM_LOAN_TEAM_REFUSED`) and 0035's re-check now asks too: a plain `team_loans` insert takes the lock and `refuse_write_by_stale_admin()`, which re-reads the caller and both conjuncts after it, closing 18.2's residual races. A team is not archived while a live loan to it ends on or after the organization's today (23514 `TEAM_HAS_LOANS`, a BEFORE trigger ordered after the caller's re-check); a wholly past loan does not block. A removal leaves `conflict_resolutions` as a team move does: a resolution keyed to the loan team matches no collision once the member is off it (AD-4's load-bearing `team_id`). The history pairs the amend on `member_id` (`AMEND_KEYS`); the loan's record and wording are 18.5's.

### AD-3 — Illegal states are made unrepresentable, not validated

- **Binds:** CAP-3, CAP-4, CAP-8, CAP-15, CAP-19, CAP-24; engine-rules R1.5, R1.6, R4.4, R9.4; quality-requirements Q6
- **Prevents:** a guard existing only in client code, so a direct PostgREST call writes a state the engine cannot interpret.
- **Rule:** Prefer schema shape to a check. Hour bands store a name and start time only, windows derived. A rotation offset is a foreign key to a step **of that pattern**, never an integer. Overlapping leave is refused by `EXCLUDE USING gist (member_id WITH =, during WITH &&)`, which requires the `btree_gist` extension. A validation that could have been a shape is a defect.
- **Named exception:** Q6 — an organization may never be left with zero admins and the last admin's role may not be downgraded — is the one refusal that *cannot* be made unrepresentable, because it is a cross-row cardinality rule. It is enforced by a constraint trigger, and it is the only constraint trigger and the only cardinality rule enforced by trigger that is permitted. A second one is a signal that AD-9's no-server-tier decision needs revisiting, not that another trigger should be written. The one other refusing trigger is the named, non-computing exception below (story 9.2); any further refusing trigger needs its own named exception here. *(Superseded 2026-11-16 by the epic 14 retro A5 inventory below, which lists every refusing trigger, 0023's second last-admin trigger among them; the constraint-trigger rule stands.)*
- **Named exception (story 9.2, human decision 2026-10-27):** a leave request may not share a date with its member's live leave (R9.4). The rule crosses `leave_requests` and `leave_records`, and no exclusion constraint can span two tables, so the BEFORE INSERT row trigger `refuse_leave_request_over_leave()` (0040) refuses it with 23P01 and the message `LEAVE_REQUEST_OVERLAPS_LEAVE`. It computes nothing: it reads whether a live leave range of the same member overlaps the new one. It acts only for a request session whose caller is an active account inserting for its own member row, and leaves every other insert to the policy's 42501. The overlap between two pending requests of one member stays schema shape: `EXCLUDE USING gist (member_id WITH =, during WITH &&) WHERE (closed_at IS NULL)`. An admin's direct leave record is never refused because a pending request overlaps it; the approval then aborts on the leave exclusion.
- **Amended 2026-10-30 (retro 8–9 item 17, 0047; recording 0041 too).** The same trigger, behind the same gates, also refuses a request reaching a date on which its member is inactive (55000 `LEAVE_REQUEST_MEMBER_INACTIVE`, 0041) and, first, a request whose first day is before `organization_today(organization_id)` (55000 `LEAVE_REQUEST_IN_PAST`, product owner decision 2026-10-30): a member requests leave from today on, and past leave is an admin's leave record, which no rule here touches. Each compares the new row with a fact read as it stands (the organization's date in its own zone, the member's status, a live range); none derives a schedule or a balance, and none is a new trigger. What became of an approved request's leave record (amended or removed since) is derived on read by the SECURITY INVOKER computed field `leave_record_change(leave_request_decisions)`, and is no stored state.
- **Amended 2026-11-16 (Architect pass for Epic 14, applied by story 14.1).** A second permitted trigger class: **append-only audit triggers**, which copy a row write of an audited organization table (AD-11's list) into `audit_events`. One function, `private.record_audit_event()` — SECURITY DEFINER, owned by the migration owner, `search_path = ''`, every name qualified, execute revoked from `public`, `anon`, `authenticated` and `service_role` — is attached to each audited table as two AFTER ROW triggers: `<table>_audit` (INSERT OR DELETE) and `<table>_audit_update` (UPDATE, `WHEN (old.* IS DISTINCT FROM new.*)`, so a no-op update records nothing). Its two `tg_argv` name the organization column and the key column (`organizations`: `id`, `id`; `leave_request_decisions` and `swap_request_decisions`: `organization_id`, `request_id`; every other table `organization_id`, `id`). It inserts one row of `to_jsonb(OLD)`/`to_jsonb(NEW)`, `auth.uid()`, `current_setting('role')`, `pg_current_xact_id()` and `now()`, reads no other table, computes nothing and refuses nothing, and is never gated on `pg_trigger_depth()`, so a write made by a definer RPC or a nested trigger (0041's deactivation close) is recorded too. It is the class 13.1's `organizations_seed_absence_types` already belongs to, so it is no refusing trigger and adds none: the Q6 constraint trigger and the 9.2 named exception stay the refusing triggers this AD names. An event commits or rolls back with the write it records, so history holds only committed writes. The refusing triggers that 0023, 0031, 0035, 0036 and 0039 ship as "ordinary triggers" (0023's `member_status_versions_keeps_an_admin`, a second trigger-enforced last-admin rule, and the stale-admin, archived, in-rotation, off-leave and TRUNCATE refusals) are not named in this AD; that gap is recorded for reconciliation and is not ratified by this pass. *(Closed 2026-11-16 by the epic 14 retro A5 inventory below.)*

### AD-4 — A conflict is derived; only its resolution is stored

- **Binds:** CAP-16, CAP-19; engine-rules R6.1–R6.5; quality-requirements Q11
- **Prevents:** a missed recomputation path producing a silent false negative — the exact failure the product exists to prevent — and stale conflict rows surviving a rotation change as false positives.
- **Rule:** No conflicts table. A collision is `leave ∩ working shift ∩ roster`, computed on read. A `conflict_resolutions` row keyed by `(organization_id, member_id, date, team_id)` records the kind, the shift type the key had when it was decided (`shift_type_id`, since 0038; null on older rows), the acting admin, and the timestamp — `team_id` is load-bearing, because a roster override can place a member on another team's shift on a date they already work, producing two distinct collisions the same day; replace-member and amend-leave also reference the override or leave change they caused. An unresolved conflict is a derived collision with no matching resolution. A replace-member resolution matches only while the override it references is live, in force and applied on that date (story 5.5d, decided in the browser, never by a roster computed in the database); removing that override ends the resolution in the same call (0033), so the key can be decided again. A resolution with a stored shift type matches only while the team's schedule has that same type on its date today (0038, decided in the browser's one resolution filter, `effectiveResolutionsOf`), so a decision left dormant when its key stopped colliding never re-applies to a different shift; a row with no stored type matches by key alone. A new decision on the key naming another type supersedes the stored one in the same insert (soft-removed, attributed to the new decision's author), comparing stored values only, so the database still derives no schedule.
- **Amendment (story 9.2):** *Za odluku* is a union of three sets: derived collisions that have no resolution, pending leave requests, and (in Epic 12) pending swap requests. Requests are stored rows (`leave_requests`, 0040), and only a decision clears one: `decide_leave_request` writes one `leave_request_decisions` row per request, keyed by the request, and the member's `withdraw_leave_request` closes it with no decision. A request's status is derived and never stored twice: pending is `closed_at IS NULL`, approved or rejected is the decision's `outcome`, and a closed request with no decision is withdrawn. A pending request derives nothing: it is no leave record, so it raises no collision and charges no balance. An approval only adds leave, so it can add collisions and erase none, and AD-5's erasure diff does not apply to it. There is still no conflicts table.
- **Amendment (story 12.1, 0049):** the third set is swap requests waiting for an admin: open (`closed_at IS NULL`) and accepted by the addressee. A swap is a stored row (`swap_requests`), and only a decision clears an accepted one: `decide_swap_request` writes one `swap_request_decisions` row per swap, keyed by the swap. Its status is derived and never stored twice: open with no answer is proposed; open and accepted waits for an admin; closed and declined is declined (`answer_swap_request` closes a decline in the same call); closed with a decision is the decision's `outcome` (approved, rejected, or `deactivated` when a party's deactivation closed it, as 0041 does for leave); closed otherwise is withdrawn, and `closed_by` says by whom. A proposed or accepted swap derives nothing (R9.1): it is no roster override, so it moves no shift, hour, collision or staffing figure. An approval writes ordinary roster overrides (the proposer off and the addressee on the given shift, and the reverse on the return shift when there is one), attributed to the admin and carrying the reason the screen supplies; the decision names them, so "this override is a swap" is structural and `roster_overrides` is unchanged. Those overrides change the projected schedule, so unlike a leave approval a swap approval is not exempt from AD-5's erasure diff (story 12.4). Whether the given shift is on the proposer's roster, or the return shift on the addressee's, is the browser's domain question (12.2 when sent, 12.4's stale check when approved); the database never projects a roster. Both checks, and AD-5's erasure diff, run on the screens alone: a direct insert bypasses the send-time check, and an admin's direct `rpc/decide_swap_request` call bypasses the stale check and the erasure diff, as every direct roster override insert already bypasses the diff. Such an approval writes overrides the domain treats as inert when they do not apply.

### AD-5 — A configuration change diffs the collision set and surfaces what it would erase

- **Binds:** CAP-9, CAP-16; engine-rules R6.3
- **Prevents:** a rotation or roster change silently deleting an unresolved conflict an admin had queued — the failure mode AD-4 opens up.
- **Rule:** Any write that can change the projected schedule computes the unresolved collision set before and after, and surfaces every erased collision for explicit confirm, amend, or discard. The change is not applied until they are dispositioned. This never blocks on warnings — only on erasures. The diff is bounded, not unbounded over all future dates: a collision requires a leave record, so the window is the union of existing leave ranges intersected with the change's own validity range. As shipped for the rotation save (story 5.5a): `domain/collisions` owns the bound (`leaveRecordsFrom`, leave clipped to the change's effective date onward) and the set difference (`erasedCollisionsOf`, unresolved keys before minus after, through the one resolution filter); "after" is the snapshot with the draft's versions and a save stamp newer than every override, so overrides from the effective date go pending as a real save makes them. Added collisions are never erasures. Each erasure is confirmed row by row in the save's dialog; nothing is recorded. A diff that cannot be derived refuses the save. Since story 5.5b the calendar roster overrides are guarded too, saving a change and removing one, through the same diff and dialog. Since story 5.5e so are the member page's team move (to another team or to no team, and withdrawing a scheduled move) and status change (deactivation, and withdrawing a scheduled reactivation): "after" changes only that member's versions, and a version already dated the day, a scheduled version gone or a missing or archived team is the write's own refusal. Since story 5.5f so are the calendar's shift-type overrides, setting one in the day detail and removing one: one surface-neutral "after" covers every override write (a set appends an override newer than every instant and unconfirmed; a removal filters it out; a confirm stamps it newest; an amend replaces it with a newest one of the new type), and a live override already on the team and date, an override gone, or an archived team or type is the write's own refusal. Every removal is checked against the fresh read; one pending review there is not applied, lists nothing, and removes at once. A set's preflight is run again on the day as the check read it. Since story 5.5g so is cancelling a scheduled rotation change: "after" is the snapshot without the active teams' versions and save stamps dated the scheduled day (an archived team's are kept, as the delete keeps them; the steps stay; no stamp is added, so the overrides the cancelled stamp had made pending are in force again), the diff runs from the scheduled date, and a calendar and rotation read that disagree on the active teams or on the scheduled versions themselves (team, pattern, offset step, anchor) cannot be checked. A fresh rotation that no longer schedules the confirmed date, or a dialog saved after the organization's day has turned, is the cancel's own stale refusal; a landed cancel re-reads the calendar, the leave and the resolutions. Since story 5.5h so is the rotation builder's override review, confirming or amending an override a rotation change left pending: the same surface-neutral "after" (a confirm stamps it newest; an amend replaces it with a newest one of the new type), the override matched by id in the fresh calendar and the diff run from its date. The row's own offers (no version governs the date) and the amend's preflight refuse first, with no check; an override gone, an archived team or type, or (for a confirm since 0035, and for an amend since 0036) a version governing the override's date other than the one the review was derived from is the review's own stale refusal. A landed confirm or amend re-reads the calendar, the leave and the resolutions beside the rotation. Discarding a pending override is never checked, since it is not applied. Since 0039 the same review disposes of a pending roster override, guarded the same way: a confirm (`confirm_roster_override`) stamps it newest, and an amend of who arrives (`amend_roster_override`, the member taken off kept) replaces it with a newest one putting the new member on, both in the calendar roster guard's "after" (5.5b's), the override matched by id and the diff run from its date. Both definers take the organization lock and carry the governing version's save time, as 0035 and 0036 do for the shift-type layer; an override gone, an archived team, the new member already put on by another live change, or another governing version is the review's own stale refusal. An amend moves the live `replace_member` resolution linked to the old row onto the new one; a removal still ends it. The roster override's pending rule reads `confirmed_at ?? created_at`, as the shift-type layer's does.
- **Amended 2026-11-21 (story 18.3).** A loan's save is a write that changes the projected schedule, so it is guarded too. "After" is the calendar snapshot with the draft loan appended to the lent member's `members` entry (and to the viewer when the viewer is the member); memberships, rotations and overrides are unchanged (R11.5). The diff runs from the loan's first date over the three core reads, fresh. A team missing from the read or archived, the member's home team on any covered date, a live loan of the member sharing a date, or a reversed range is the write's own refusal, before any diff. *Što se mijenja* derives from the same "after": the shifts lost and gained per date, two teams' working shifts at once and work joined with no rest over the range and a day either side, the short-staffed block for both teams, and every roster override in force in the range that applies before and not after. Such an override is listed and kept, never discarded; the admin removes it from the calendar's day detail. Everything but an erasure warns and never blocks. Amending, ending early and removing a loan (story 18.4) take the same rule.
- **Amended 2026-11-21 (story 18.4).** An amend or a removal of a loan is guarded by the same rule. Its "after" is the member's loans with the old one replaced by the draft (amend) or without it (removal), and the diff, *Što se mijenja* and the short-staffed block run over the change's window: from the earlier first date to the later last date of the old and new ranges (a removal: the old range). The amended loan gone from the fresh read, the home team or an archived team, a reversed range, or another live loan of the member sharing a date is the write's own refusal, before any diff. A removal returns every covered date to what it would be with no loan ever recorded. Dates the member is inactive on are a warning line, never a refusal.

### AD-6 — Time is integer minutes since midnight, over nominal wall-clock

- **Binds:** CAP-3, CAP-7, CAP-14; engine-rules R3.1–R3.10; DI-5, DI-6
- **Prevents:** the whole daylight-saving class of bug, and a second unit reaching for elapsed real time because it was available.
- **Rule:** No `Date`, no `timestamptz`, and no instant enters a calculation. Shift types store `start_time`/`end_time` as `time` plus `is_working`; nominal duration is derived (`end <= start` means it crosses midnight, add 1440). Instants are computed for display in the organization timezone only, and never for accounting.

- **Amended 2026-11-21 (Architect pass 1) — zone arithmetic at the edges.** Every rule stays nominal wall-clock minutes, and no instant enters a calculation of hours, leave, rosters or conflicts. Two consumers need an instant: a reminder's due time (`remind`) and a calendar's timezone definition (`@shift/ics`, AD-20). Both get it from **one** domain module, `packages/domain/src/zone.ts`. It converts an organization-local date and minute to an instant, and lists a zone's offset transitions over a range. It uses only the runtime's built-in `Intl` (no timezone library, no I/O), and it is the only domain module that names `Intl`. An "N hours before" lead is the shift start's real instant minus N hours, so on a DST date it is N real hours (FR-86). "The evening before" is 20:00 local on the day before the shift's start date. A half day's lead counts from the worked half's start (R12.2). The due instant is one exported function beside the conversion (`reminderDueAt(lead, date, startMinute, zone)`; the story may rename it), and `remind` never computes it inline. The domain's purity test also asserts that no domain module other than `zone.ts` names `Intl` or `Date`. The runtime-parity test (AD-19) covers both DST dates of both years in its window. A second local-to-UTC conversion anywhere, in a function, in SQL or in `apps/web`'s download, is a defect.
- **Amended 2026-11-21 (16.2) — `zone.ts` as shipped.** It exports `instantOf(date, minute, zone)` (epoch milliseconds; `minute` 0–2879, so a midnight-crossing end is written on its start date), `offsetMinutesAt(instant, zone)` (minutes east of UTC), `utcIsoOf(instant)` (`YYYY-MM-DDTHH:MM:SSZ`), `zoneTransitionsOf(zone, from, to)` (each transition's first instant and the offsets either side, local dates both inclusive, at most 4018 days) and `checkTimeZone(zone)`. A local time a transition skips is read with the offset before the gap, and a repeated one is its earlier instant (RFC 5545 §3.3.5's and Temporal's "compatible"). It names `Intl` and no `Date`; the purity test strips comments and strings and finds `Intl` or `Date` in no other module. `reminderDueAt` is not in 16.2: the lead kinds are 17.2's, and it lands there beside these. Which transition is "the last one before the window" (AD-20) is `@shift/ics`'s choice over `zoneTransitionsOf` (16.4).

### AD-11 — Attribution comes from column defaults the client cannot forge

- **Binds:** CAP-9, CAP-12, CAP-16, CAP-24; DI-11; quality-requirements Q11, Q12
- **Prevents:** an unattributable or falsely attributed change — which matters more than usual because AD-9 leaves no server tier to enforce it.

- **Amended 2026-11-16 (Architect pass for Epic 14, applied by story 14.1; decision D4).**

### AD-12 — Identity is an admin-issued username mapped to a synthesized address

- **Binds:** CAP-1, CAP-4; quality-requirements Q5
- **Prevents:** an unbuildable requirement. Supabase Auth binds a password to an email or phone and has no username identity, while CAP-1 requires a usable account with no email present.
- **Rule:** Members sign in with a username; the app resolves it to a non-routable synthesized address in `auth.users`. **Consequence:** email-based self-service reset is impossible for these accounts, so password reset is an admin-issued action. The credential an admin issues or resets is a one-time one: the member's next sign-in sets their own before anything else (AD-16, story 7.8). No phone number is collected.

### AD-16 — One privileged auth boundary, and it may not think

- **Binds:** CAP-1, CAP-4; quality-requirements Q2, Q5, Q8
- **Prevents:** two failures at once. Without it, `admin.createUser` has nowhere to run and CAP-1's admin-issued credentials are unbuildable; without its second clause, the one component holding the secret becomes the place every awkward rule migrates to, and AD-7's leaf property dies quietly.
- **Rule:** Exactly one Edge Function holds the secret key. It exposes four operations. `createUser`, `updateUserById` and `resetPassword` are each callable only by an admin of the target member's own organization, verified against the database rather than the request. `clearMustSetPassword` (story 7.8) is open to any role and acts only on the caller: it names its target by `auth.getUser(<caller's JWT>)`, never by a value in the request, and writes nothing but that account's flag. It **performs no domain calculation and contains no rule from `engine-rules.md`** — adding either is a defect, not a refactor.

  Four further clauses, because the secret key bypasses RLS entirely:

  - **The first sign-in is held behind a flag** (story 7.8). `createUser` and `resetPassword` set `app_metadata.must_set_password = true` on the account they issue or reset. Only the secret key writes `app_metadata`, so a member cannot clear it with their own `updateUser`. The member sets their own password through GoTrue as themselves, then calls `clearMustSetPassword`, which writes `false` for the caller only and changes neither the password nor any session. The route guard (`_app`) keeps every destination closed while the flag is set. The flag needs no migration, and it is never kept in `user_metadata`.

  - **The function holds two clients.** The secret key is used *only* for the auth call. Every domain-table write it makes — the `members` row above all — goes through a client built from the **caller's JWT**, so RLS, AD-11's `auth.uid()` defaults and its `WITH CHECK` all still apply. A domain write made with the secret key is a defect.
  - **Organization provisioning does not use this function.** It is an operator CLI task outside the application, and is the single write in the system exempt from AD-11 — no admin exists yet to attribute it to.
  - **Deactivation does not use this function either** (amended by story 1.6, human decision 2026-09-23). Active status is a versioned domain table (AD-2) written through PostgREST under RLS like every other domain write (AD-9): a change is an inserted version, and a change not yet in effect may be cancelled by deleting it; a version in effect is never changed or deleted. Data access ends on the effective date because the AD-10 helper reads the version covering today in the organization's timezone; sign-in and refresh end because the custom access token hook refuses a member inactive today. There is no `ban`/`unban` and no write to the auth store: the secret key could only have added a session revocation, which GoTrue does not offer without a password change. A token minted before the date keeps authenticating to GoTrue's own endpoints until it expires and reads no organization data. Deactivation is the only way a member leaves (0036): no session deletes a `members` row, so a member's status, team and leave history outlive them.

- **Amended 2026-11-21 (Architect pass 1) — re-scoped.** "Exactly one Edge Function holds the secret key" now reads: exactly one Edge Function holds the secret key **for the auth API**. `notify` (since 10.1) and `remind` hold it only to call their own `service_role`-only RPCs (AD-14, AD-17). This AD's no-rule, no-calculation clause binds `admin-auth` unchanged.

- **Amended 2026-11-21 (Architect pass 2) — the second identity kind in `admin-auth`** *(AD-12; stories 19.1, 19.2; proposal §8 risk 6)*. Organization creation by signup does not use this function either. It is `create_organization`, in SQL (AD-23), because it needs no secret key.
  - **`createUser`** is unchanged. It issues username identities only.
  - **`updateUserById`** changes nothing in its order. Its first write, the caller-client `members` update, is refused by the database for an email identity (AD-3's `members_username_follows_email_identity`, 23514 `SIGN_IN_IS_EMAIL`). `admin-auth` maps that refusal to 409 `SIGN_IN_IS_EMAIL` and makes no auth call.   - **`clearMustSetPassword`** acts only on the caller. For a claimless account it writes that account's own flag, which is unset anyway. It reads and grants nothing, so 19.1 asserts it is harmless.
  - Mapping a database refusal to a reply is what `membersRefusal` already does. It is no rule from `engine-rules.md`, and the no-rule clause holds.

### AD-18 — A notification is written by the request that asserts its fact

- **Binds:** CAP-20; localization L4; quality-requirements Q25
- **Prevents:** a notifier that computes its own answer (a second home for domain logic), and a notification for a fact that was rolled back.
- **Rule:** A notification is written to the outbox by the same request that asserts the fact it reports (an approval, a decision, a roster change), as codes and operands. `notify` computes no domain answer. A reminder that needs projection is out of v1.
- **As shipped (story 10.1, 0042):** `notification_outbox` is organization-scoped, row level security on with no policy, and no table privilege for `anon`, `authenticated` or `service_role`. A row holds `code`, `operands`, `subject_id`, `recipient_member_id` and `channel` (`email`), never prose and never an address; the unique key (`code`, `subject_id`, `recipient_member_id`, `channel`) makes it at most once per recipient and channel. `decide_leave_request` inserts `LEAVE_REQUEST_APPROVED` or `LEAVE_REQUEST_REJECTED` with `{startDate, endDate}` for the requester in its own transaction; 0041's deactivation close writes none. Delivery: email rows only; a claim lease of 10 minutes with `claimed_at` as the settle's token; at most 5 attempts; Resend's `Idempotency-Key` = the row id. A transient failure (network, 408, 409, 429, 5xx, or a code the deployed function cannot render yet) releases the claim and backs off attempts × 10 minutes; 401 or 403 stops the run and gives every held row back without spending its attempt, as does the run's 45 s budget (amended 2026-10-30 by the retro-10 batch, see AD-14: the stop and the budget are per channel — Resend's refusal holds email rows only, and push rows have their own 35 s start); any other 4xx fails the row. A failed send never blocks or rolls back the decision. Story 10.2 adds the other events.
- **As shipped (stories 10.2–10.4, 0043–0046).** Every other event is written by definer AFTER triggers on the fact tables (0043: `leave_records`, `roster_overrides`, `shift_type_overrides`, `rotation_assignments`, `leave_requests`), in the transaction of the write, through one helper, `private.notify_members`. The recipients are stored facts only, and one rule applies to every event on both channels: never the member whose session made the write, only a member active in the organization's today, an `email` row only for a member with an address, and (0045) a `push` row only for a member with at least one device. From 0046 `decide_leave_request` writes its rows through the same helper, so the decision follows that rule too (product owner, 2026-10-30). A fact wholly in the past notifies nobody; the transaction-local `shift.notify_suppress` (`approval`, `amend`) makes an amend one `*_CHANGED` and an approval only the decision. 0044 adds the member's `notification_settings` and the organization's `email_notifications` switch, enforced by one definer BEFORE INSERT filter on the outbox that drops `email` rows only, and again at claim time (`EMAIL_TURNED_OFF`). The channels are independent: nothing about email holds or fails a push row, and the reverse.
- **Amended 2026-11-21 (story 18.4, 0064).** `private.notify_team_loan()` is replaced in place and also bound to the removal (`team_loans_notify_removal`). 0043's `shift.notify_suppress = 'amend'` flag around the amend's two writes makes it one `LOAN_CHANGED` (the replacement's dates and team) to the member when the old or the new range is current, never a `LOAN_MADE`; a removal is `LOAN_REMOVED` when the loan was current. No reason, no author.

- **Amended 2026-11-21 (Architect pass 1) — the one exception: a shift reminder** *(channels ratified by the founder 2026-11-21 (D-S6); stories 17.2 and 17.3)*.
  - **What it is.** A shift reminder is the only notification that no request asserts. `remind` writes it from the canonical projection (AD-7, AD-19), as codes and operands, through the `service_role`-only `enqueue_shift_reminders(p_items jsonb)`.
  - **The re-check.** For each item that RPC confirms, at write time, that the member is active in the organization's today and still has that lead on. A setting turned off since the read wins.
  - **The lead codes.** One closed set, `H1 | H2 | H3 | H6 | H12 | EVENING_BEFORE`, exported once from `packages/domain`. The `reminder_settings` check, the RPCs, the due function and `notify`'s variant map use exactly that spelling, held equal by a root test.
  - **The settings row** (17.1; it is the AD-2 row for reminder settings). `reminder_settings(organization_id, member_id, leads text[] not null default '{}', email boolean not null default false)`. `leads` holds at most two distinct codes from the set. Reminders are on exactly when `cardinality(leads) > 0`, with no separate flag. No row means off (D4).
  - **The key.** The RPC computes `subject_id` in SQL as `md5('SHIFT_REMINDER:' || member || ':' || date || ':' || team || ':' || lead)::uuid`, where team is the effective team after loans (`uuid-ossp` is not installed). With the existing unique key (`code`, `subject_id`, `recipient_member_id`, `channel`), each reminder is written at most once, whatever runs overlap.
  - **The row.** Code `SHIFT_REMINDER`. The operands are `{ date, teamId, start, end, startsAt, lead, leadHours, shiftTypeName, teamName }`:
    - `start` and `end` are minutes. `notify` formats them as `HH:MM` through a `TIME_OPERANDS` set beside `DATE_OPERANDS`.
    - `leadHours` is an integer, absent for `EVENING_BEFORE`. `notify` picks the template variant (`Sutra radiš …` or `Za {n} h radiš …`) from the lead and parses nothing.
    - `enqueue_shift_reminders` looks up the two names in SQL from the item's ids, as they stand at write time, and trusts no display text in `p_items`.
    - The link is `/kalendar?mjesec=<YYYY-MM>&dan=<date>&danSmjena=<teamId>`, through the existing sign-in path. A reminder email's footer points to *Obavijesti → Podsjetnici*.
  - **The channels, through the one recipient rule** *(D-S6)*. The RPC writes through the existing `private.notify_members`, so a reminder obeys every event's recipient rule: active in today, an address for `email`, a device for `push`. The reminder email switch is enforced where the other email switches are: `private.filter_notification_outbox()` drops a `SHIFT_REMINDER` email row while `reminder_settings.email` is off, and the claim settles one queued before the switch went off as `EMAIL_TURNED_OFF`. So a reminder email needs the address, the reminder switch, the member's email switch and the organization's switch. That conjunction is one SQL predicate, `private.reminder_email_on(member)`, read both by 17.1's screen, which shows the channel each reminder will use, and by the filter.
  - **Claim-time expiry.** `claim_notifications` settles a `SHIFT_REMINDER` row `REMINDER_EXPIRED` once `now() >= startsAt`, and `REMINDER_TURNED_OFF` when the member no longer has that lead. Neither is a domain answer: both are a comparison and a lookup. `notify` sends a reminder push with `TTL = max(0, startsAt − now)`, never the default day. So a backoff, a backlog or an offline device never delivers a reminder after the shift has started.
  - **No retraction.** A reminder is never retracted. A later change to the shift is reported by the existing change notifications (D5).
  - **No new column.** The outbox gains no `send_after` column: computing a reminder at most 5 minutes before it is due makes one unnecessary (AD-14).
  - This resolves the Deferred entry "Shift reminders". The rule's last sentence, "a reminder that needs projection is out of v1", is superseded.

### AD-19 — A server projection reads one assembly, held equal to the browser's

- **Binds:** CAP-25, CAP-26; NFR-19, NFR-28; quality-requirements Q27
- **Prevents:** a second read layer on the server that drifts from the browser's (`sprint-change-proposal-2026-11-20-v2-scope.md` §8, risk 3). Without it, `calendar-feed` and `remind` would each build the domain's inputs their own way, and a new rule kind would land in one and not the other.
- **Rule (Architect pass 1, 2026-11-21; story 16.2).** Every server projection gets its asserted rows from **one** SQL function, `private.member_schedule_inputs(p_member uuid, p_from date, p_to date)`. It is `SECURITY DEFINER`, and no role may execute it: only the two definer entry points of AD-14 call it (`calendar_feed_inputs`, `reminder_inputs`).
  - **What it returns.** One `jsonb`, already in the domain's input shapes (the camelCase keys the domain's types name), and nothing derived (AD-1):
    - the organization's id and zone;
    - the teams (id, name, archived);
    - the shift types with their versions;
    - the rotation steps, and the assignments with their creation stamps;
    - every member's id, membership versions, status versions and live loans, with no name, rank or address;
    - the live shift-type overrides and roster overrides dated in the window, with no reason and no author;
    - the **one** member's own leave records that overlap the window (dates, half, absence type id), with no type name and no reason.
  - **The type.** The assembly is one exported domain type, `ScheduleInputs` (the story may rename it), stamps included. Shift-type and roster overrides carry `writtenAt` (integer µs, `confirmed_at ?? created_at`), and rotation versions carry their `RotationVersionStamp`, because `overrideStandingOf` needs both to leave an override pending review. The SQL writes µs as `(extract(epoch from t) * 1000000)::bigint`, which is exact under PostgreSQL 17's numeric `extract`, the same value `instantMicrosOf` gives in the browser.
  - **Live.** "Live" is the predicate the `calendar_*` RPCs already use, through one shared SQL helper, never restated.
  - **Windowing.** Versioned rules come whole, as the browser reads them. Overrides are filtered by date, and loans and leave by overlap with the window.
  - **What the server projects.** R12 only. So the assembly carries no hour bands, no absence-type names and no other member's leave.
  - **What a function adds.** It validates the assembly with the domain's own preconditions (`checkLoans`, `checkRosterOverrides`, …) and projects. It maps no rows of its own.
  - **Parity, in two tests**, both run in CI:

### AD-20 — The calendar is serialized by one pure package

- **Binds:** CAP-25; FR-81, FR-83
- **Prevents:** the feed and the browser's "download this month as `.ics`" (16.5) serializing the same shifts two ways, and a timezone block that disagrees with the events.
- **Rule (Architect pass 1, 2026-11-21; stories 16.4 and 16.5).** `packages/ics` (`@shift/ics`) holds the RFC 5545 subset: `VCALENDAR`, `VTIMEZONE` and `VEVENT`, with CRLF line ends, 75-octet folding and TEXT escaping, all written by hand and checked against golden files. It has zero runtime dependencies, may import `@shift/domain` and nothing else, and is consumed under AD-7's resolution rule by `calendar-feed` and by `apps/web`. It is not in `packages/domain`, because it is serialization, not a rule.
  - **The calendar** *(contents ratified by the founder 2026-11-21 (D-S2))*:
    - `PRODID`, `VERSION:2.0`, `CALSCALE:GREGORIAN`, `METHOD:PUBLISH`, `X-WR-TIMEZONE` set to the organization's zone, and a fixed product name as `NAME` and `X-WR-CALNAME`, so no client shows the secret URL as the calendar's name;
    - **one `VTIMEZONE`** whose `TZID` is the organization's IANA name. It holds one `STANDARD` or `DAYLIGHT` observance per offset transition, from the last one before the window through the last one inside it, each with an explicit `DTSTART`, `TZOFFSETFROM` and `TZOFFSETTO` and no `RRULE`, all derived from `zone.ts` (AD-6). A zone with no transition has one `STANDARD` observance at its constant offset. The serializer takes the window as an argument: the feed passes D2's, and the download passes the month;
    - **one `VEVENT` per R12 shift**:
      - `UID` is `<date>-<teamId>-<memberId>@shift`: opaque ids, stable per member, date and team (FR-81). The month download uses the same UIDs with `@shift-download`, so importing it into a calendar that subscribes to the feed duplicates rather than collides *(pending D-S2)*;
      - `DTSTART;TZID=` and `DTEND;TZID=` are local wall-clock times. A midnight-crossing shift ends on the next date (DI-5), and a half day uses the worked half's interval (R12.2);
      - `SUMMARY` is the shift type's name and the team's name, and nothing more;
      - `DTSTAMP` is the request instant;
      - there is no `DESCRIPTION`, `LOCATION`, `ATTENDEE` or `ORGANIZER`.
  - An event's `DTSTART` and `DTEND` are never UTC-only or floating. `DTSTAMP` is UTC and an observance's `DTSTART` is local, as RFC 5545 requires. Google and Apple use the IANA `TZID`. This observance shape is unverified on Outlook: 16.4 checks it once by hand, or records it as an accepted risk.

### AD-21 — The signup door is shut unless every switch opens it

- **Binds:** CAP-28; FR-93, FR-98; NFR-29; Q30; D-S3, D-S4, D-S5 (ratified 2026-11-21)
- **Prevents:** signup opening in production through a change nobody meant as that decision: a default flipped in the shared compose file, a staging value copied over, or a build variable. It also prevents a door opened with autoconfirm still on, which would let an unverified address found an organization.
- **Rule (Architect pass 2, 2026-11-21; story 19.1).** Signup is open on a stack only while three switches are all open. Each is shut by default.
  1. **GoTrue's environment.** The compose reads `GOTRUE_DISABLE_SIGNUP=${SHIFT_DISABLE_SIGNUP:-true}` and `GOTRUE_MAILER_AUTOCONFIRM=${SHIFT_MAILER_AUTOCONFIRM:-true}`. `staging.env.example` sets both to `false`. `production.env.example` sets both to `true`. The parity test fails if either the compose default or the production example opens the door. The test also pins `config.toml` to staging's values. Locally, `[auth] enable_signup = true` and `[auth.email] enable_confirmations = true`, and the CLI's mail catcher receives the mail. Admin-created and seeded accounts are confirmed when created; 19.1 verifies the seed.
  2. **The database.** `private.signup_settings` is a singleton: `id boolean primary key default true check (id)`, plus `open boolean not null default false`, `accounts_per_day`, `organizations_per_day` and `attempts_per_account`. The last three are positive integers defaulting to 100, 20 and 10. The migration seeds it. No session holds a privilege on it. The operator opens it on staging by SQL over the tailnet (DEPLOY.md). Closing it stops new accounts and new organizations at once (AD-23): it is the circuit breaker.
  3. **The SPA.** `VITE_SIGNUP_ENABLED` renders `/registracija`, the *Prijava* link to it and `/zaboravljena-lozinka`. This switch is cosmetic, not a control. `require-config.mjs` refuses it for the production environment, so opening production starts with a reviewed PR.
  - **GoTrue will not run an open door half-built.** The auth service's entrypoint wrapper is tested by running it under `sh`, as Kong's is.
    - It first refuses any boolean it reads that is not exactly `true` or `false`. GoTrue parses booleans with Go's `ParseBool`, which also takes `0`, `f` and `False`.
    - Then, when `GOTRUE_DISABLE_SIGNUP=false`, it exits non-zero unless all of these hold:
      - `GOTRUE_MAILER_AUTOCONFIRM=false`;
      - the SMTP host, user, password and admin address are set (AD-17);
      - the before-user-created hook is enabled;
      - `GOTRUE_RATE_LIMIT_HEADER` is set (GoTrue's per-IP limits are off without it);
      - `GOTRUE_MAILER_OTP_EXP` is 3600 or less and `GOTRUE_MAILER_OTP_LENGTH=10`;
      - each `GOTRUE_MAILER_TEMPLATES_*` URL answers 200 with a body that contains `token_hash`. GoTrue falls back to its default English template when a fetch fails, and that template links to a GET on `/verify`. Kong refuses that GET (AD-22), so a fallback mail is useless rather than consumable.
  - **The before-user-created hook** (`public.before_user_created_hook`, AD-10) is `SECURITY DEFINER` with `search_path = ''`, executable by `supabase_auth_admin` only. It answers one refusal, `{ "error": { "http_code": 403, "message": "SIGNUP_REFUSED" } }`, for every one of these reasons:
    - `signup_settings.open` is false;
    - the address is synthesized, or malformed by AD-12's normalization;
    - its local part would fail `members_username_check`;
    - the last 24 hours already hold `accounts_per_day` auth accounts with no `members` row.

    It writes nothing.
    - **Where GoTrue v2.196.0 runs it:** every user-creating path except `POST /admin/users`. That is `/signup`, `/otp`, `/magiclink`, `/invite`, `/admin/generate_link`, anonymous, OAuth, SAML, Web3 and OIDC id_token. Kong closes every one of those but `/signup` (AD-22).
    - **What it cannot guarantee.** It runs only for an address with no user yet, so its refusal depends on the address, and AD-22 hides that. It runs outside a transaction, so `accounts_per_day` is approximate under concurrency.
  - **Per-IP limits, in Kong.** These use Kong 2.8.1's bundled `rate-limiting` plugin, added to `KONG_PLUGINS`, with `limit_by: ip` (the client address resolved below), `policy: local` and `hide_client_headers: true`. The routes are AD-22's. Coolify chains every label-defined Traefik middleware onto its catch-all routers for the whole host, so Traefik labels are not used. Staging defaults, each a compose variable:
    - `auth-v1-mail` (signup, recover and resend together): 5 an hour and 20 a day;
    - `/auth/v1/token`: 120 per 5 minutes, because refresh grants share it and one station's devices sit behind one NAT;
    - `/auth/v1/verify`: 30 per 5 minutes;
    - `/rest/v1/rpc/create_organization`: 10 an hour.

    A 429 from Kong reads the same for every address. Production's values are set by the D-S5 checklist. **Accepted on staging, decided before production:** a ceiling that one actor can exhaust shuts signup for everyone, and IPv6 clients rotating inside one /64 escape a per-address limit. 20.5 records whether the host serves AAAA at all.
  - **The client address reaches Kong and GoTrue.** This answers the 20.1 deferral.
    - Kong: `KONG_TRUSTED_IPS=${SHIFT_PROXY_CIDR:?}`, which is Traefik's network on the host. Kong's entrypoint refuses `0.0.0.0/0` and `::/0`. Also `KONG_REAL_IP_HEADER=X-Forwarded-For`, `KONG_REAL_IP_RECURSIVE=on`, and `KONG_HEADERS=off`, so no `Via`, `Server` or `X-Kong-*-Latency` header is added. That is pinned by `test/self-hosted-stack.test.ts`.
    - GoTrue: `GOTRUE_RATE_LIMIT_HEADER=X-Real-IP`. Kong sets that header from the resolved client address and overwrites any value a client sent. GoTrue takes the header's first value.
    - GoTrue's own limits are set explicitly: `GOTRUE_RATE_LIMIT_EMAIL_SENT=10` an hour for the whole stack on staging (Resend's 100 a day is shared with `notify`), `GOTRUE_RATE_LIMIT_VERIFY=30`, `GOTRUE_RATE_LIMIT_TOKEN_REFRESH=150` and `GOTRUE_SMTP_MAX_FREQUENCY=60s`.
    - Story 20.5 confirms on the host, for IPv4 and IPv6, that Kong sees each client's own address and not Docker's gateway. It also confirms that Coolify's Traefik replaces a client's `X-Forwarded-For` (Traefik v3.7 there is not `insecure`), and checks Storage's `REQUEST_ALLOW_X_FORWARDED_PATH`.
  - **Auth email** is SMTP through Resend (AD-17), in Croatian. 19.1 builds the templates (confirmation, recovery, email change) from `hr.json`'s `signup.email` keys into `dist/auth-email/*.html` at web build. GoTrue reads them from the app origin (`GOTRUE_MAILER_TEMPLATES_*`). Their subjects are `GOTRUE_MAILER_SUBJECTS_*`. A root test pins both to `hr.json`. Every link has AD-12's `token_hash` form.
  - **Locally,** `supabase/seed.sql` opens `signup_settings` for the local stack only. `config.toml` pins `[auth] enable_signup`, `[auth.email] enable_confirmations`, `otp_expiry` and `otp_length` to staging's values, and the parity test names those four keys. The AD-10 sentence of 2026-11-20 that calls `config.toml` "the one source of truth for auth settings" now means local and staging; production's closed door lives in `production.env.example`.
  - **A dump carries the switch.** A production restore comes only from a production dump, never from staging's, which would carry `signup_settings.open = true` (DEPLOY.md's restore rule).
  - **No captcha** (D-S3). See Deferred.

### AD-22 — Every auth answer that could name an address is one answer, made at the gateway

- **Binds:** CAP-28; FR-99; NFR-29; Q28; D-S8 (ratified 2026-11-21)
- **Prevents:** an endpoint that tells a caller whether an address, account or organization exists, or that lets a caller act on an address they do not own. In GoTrue v2.196.0, as checked against its source:
  - a repeated signup of a confirmed address answers a sanitized user whose `identities` is `[]`, and skips the password hash a new signup computes;
  - a second mail to one address within `SMTP_MAX_FREQUENCY` answers 429;
  - a mail to a synthesized address fails at the provider;
  - background sending still holds the answer until the mail is sent;
  - `PUT /user` with a new email answers `email_exists` for a taken address;
  - `POST /verify` accepts an email plus a 6-digit code, which can be brute-forced;
  - AD-21's hook refuses only new addresses;
  - Kong's default headers expose GoTrue's latency.
- **Rule (Architect pass 2, 2026-11-21; stories 19.1, 19.2).** The SPA is not the boundary. **Kong's `/auth/v1/` is an allow-list.** The catch-all route `auth-v1-all` is removed. Each path below is a route of its own, and every other path is 404 from Kong's default answer for an unmatched route. That includes path variants: a trailing `/`, a doubled `/`, `;` and percent-encoding. The probe sends each variant. Each `post-function` below is in `KONG_PLUGINS`, and so is `rate-limiting` (AD-21).

  | Path | What Kong lets through, and the answer |
  | --- | --- |
  | `POST /auth/v1/signup`, `/recover`, `/resend` | **Answered at once, then forwarded.** The service `auth-v1-mail` has `key-auth`, `acl` and its limits. Its `post-function` access phase reads the body with `kong.request.get_body()` and answers `kong.response.exit(200, "{}")` every time. GoTrue never answers the client. Unless the body is unreadable, has no `email`, or holds an address that AD-12's normalization makes synthesized or malformed, it then relays the original body to GoTrue on the stack network (`http://supabase-auth:9999`) from an `ngx.timer.at(0, …)` with `resty.http`. The relay carries `X-Real-IP` set to the client's resolved address, so GoTrue's per-IP limit and audit still see the client. It logs GoTrue's status as a fixed code without the address, so a masked outage is visible in the logs and to 20.8. This needs `KONG_UNTRUSTED_LUA_SANDBOX_REQUIRES=resty.http` and the timer inside Kong's sandbox, and 19.1's rehearsal proves both. **If the sandbox does not allow them,** the fallback is the same route answering `200 {}` from `header_filter` (with `set_status`, the upstream headers cleared) and `body_filter` (`set_raw_body("{}")` only once `get_raw_body()` returns the whole body). That masks status, headers and body but not timing, and the remaining timing gap is then a founder decision (F1). |
  | `POST /auth/v1/token` | Proxied with its limit. `invalid_credentials` answers an unknown address and a wrong password alike. `email_not_confirmed` and the hook's `SIGN_IN_REFUSED` need the right password. The SPA maps `email_not_confirmed` to the neutral "confirm, or resend" screen. **Accepted residual:** a password grant for a known address takes a bcrypt comparison that an unknown one does not, the same as v1's username sign-in. It is limited per IP, and checklist B8 records it for the founder's acceptance at D-S5. |
  | `POST /auth/v1/verify` | Its own service. The `post-function` passes only a body with exactly `token_hash` and `type` (`signup`, `recovery` or `email_change`). Anything else answers 400 `{}`, so no email-plus-code body ever reaches GoTrue. `GOTRUE_MAILER_OTP_EXP=3600` and `GOTRUE_MAILER_OTP_LENGTH=10` hold even if that check is removed. `GET /auth/v1/verify` is 404: the open `auth-v1-open` verify service is removed, because no Shift link uses it (AD-12). |
  | `GET /auth/v1/user`, `PUT /auth/v1/user` | A `PUT` whose body carries `email` or `phone` answers 422 `{}` from Kong. A password or `data` change passes. So a session can neither probe addresses nor change its sign-in address (AD-12). |
  | `POST /auth/v1/logout`, `GET /auth/v1/health`, `GET /auth/v1/.well-known/jwks.json` | Proxied, as today. |
  | `/auth/v1/admin/*` | Proxied with key-auth and the `admin` ACL group only. It is reachable only with the secret key (`admin-auth`). |
  | Everything else under `/auth/v1/` (`otp`, `magiclink`, `reauthenticate`, `invite`, `authorize`, `callback`, `factors`, `sso`, `settings`, `token?grant_type=…` variants on other paths) | 404. There is no passwordless sign-in, no OAuth, and no second way to create an account. |
  | `rpc/create_organization` | AD-23: `SLUG_UNAVAILABLE` for a taken slug and a reserved one alike, limited per account and per IP. Slugs are not secret (D-S8). No surface lists organizations or slugs, and none answers an anonymous caller. |
  | `calendar-feed` | AD-14's one 404. |

  - **The probe** belongs to 19.2. It runs against 20.1's compose rehearsal stack (DEPLOY.md §9.5), never the CLI's Kong, and later against staging. It sends signup, recover and resend for a new address, a known confirmed one, a known unconfirmed one and a synthesized one, plus `/token` for a known and an unknown address. It asserts one status, one body and **one set of header names and values**. It asserts medians within one timing class, which its spec defines with the figures it measured.
  - **The SPA never reads the mail routes' bodies.** It shows UX-DR60's one screen. It checks the address shape and the password floor (10, the same constant as the set-password step) before sending, so a refusal that is masked never surprises a user who typed correctly. `/potvrda` calls `verifyOtp` only when the user clicks *Potvrdi*, never on load, so a mail scanner that runs JavaScript consumes nothing.

### AD-23 — An organization is founded by one definer, from the caller alone

- **Binds:** CAP-28; FR-94, FR-100; Q29, Q30; D-S3, D-S8, D-S9, D-S10 (ratified 2026-11-21)
- **Prevents:**
  - a provisioning path that takes an organization id, or that founds a second organization for one account;
  - an organization founded by an unverified or username identity;
  - configuration written that nobody asserted;
  - the housekeeping job (AD-25) deleting an account while it founds.
- **Rule (Architect pass 2, 2026-11-21; story 19.3).** `public.create_organization(p_name, p_slug, p_organization_type, p_timezone, p_leave_year_start_month, p_leave_year_start_day, p_admin_name, p_admin_leave_allowance_days) returns jsonb`. It is `SECURITY DEFINER` with `search_path = ''` and every name qualified. Only `authenticated` may execute it (revoked from `public`, `anon` and `service_role`). It takes no organization id, member id or address. Its steps, in order:
  1. **Lock the caller.** `select … from auth.users where id = auth.uid() for update`. No row is 42501.
  2. **The caller's state.** One refusal, 42501 `ORGANIZATION_NOT_CREATABLE`, unless every one of these holds:
     - `email_confirmed_at` is set;
     - the account is neither banned (`banned_until` in the future) nor deleted (`deleted_at`);
     - the address is not synthesized or malformed (an email identity, AD-12);
     - `raw_app_meta_data ->> 'must_set_password'` is not `true`;
     - no `members` row of any organization has `auth_user_id = auth.uid()`.

     These are facts about the caller alone.
  3. **Input.** Raised before anything is counted, because it reveals nothing about anyone else.
     - Names are trimmed exactly as the operator script trims them and checked by `private.name_key`.
     - The allowance is `>= 0`, and the leave-year day is 1–28.
     - The slug must pass 0002's rule (22023).
     - The timezone must pass `private.is_known_timezone(text)`, a new function that the operator script calls too. It is the script's rule moved into one function: a name in `pg_timezone_names`, with no `UTC` and no `posix/…` alias. An `Intl` parity vector, run under Node and the pinned edge-runtime (AD-19's runtime-parity job), keeps every zone it accepts usable by `zone.ts`. A refusal is `ORGANIZATION_TIMEZONE_UNKNOWN`.
  4. **Serialize.** `pg_advisory_xact_lock(<namespace>, <key>)`, the two-argument form, under a namespace constant of its own. So the ceiling count is exact. At 20 a day the queue is nothing.
  5. **Limits.** Insert one row into `private.organization_attempts (auth_user_id uuid not null, attempted_at timestamptz not null default now())`. It has no foreign key: an account deleted by AD-25 leaves its attempts to age out. The call answers `{ "code": "TRY_LATER" }` when any of these holds:
     - `signup_settings.open` is false;
     - the account has made more than `attempts_per_account` attempts in the last 24 hours;
     - `organizations_per_day` organizations with `founded_by` set were created in the last 24 hours.

     "Day" is a rolling 24 hours, which needs no zone. A limit is **returned, never raised**, so the attempt row commits.
  6. **The slug.** A slug that is taken, or that is reserved, answers one code: `{ "code": "SLUG_UNAVAILABLE", "proposal": … }`. That answer is returned, so it counts as an attempt.
     - **Reserved** means it fails the new check constraint `organizations_slug_not_reserved`: `admin`, `api`, `app`, `auth`, `postavljanje`, `prijava`, `registracija`, `shift`, `staging`, `www`. So the operator script cannot provision one either. The migration first checks that no existing slug is reserved.
     - **The proposal** is the first free slug from `<base>-2` to `<base>-9` that fits 63 characters, else `<base>-` and four random `[a-z0-9]` characters. It is not reserved for the caller.
     - On insert, a `unique_violation` **on the slug's constraint by name** (`organizations_slug_key`) takes the same answer. A violation of `founded_by`'s unique index is a race of one account with itself, and it raises `ORGANIZATION_NOT_CREATABLE`.
     - The answer never says that an organization holds the slug.
  7. **Write.** Insert the organization: the given fields, `locale` as the RPC's constant for the one shipped locale (pinned to the SPA's locale resource by a root test, NFR-8), and `founded_by = auth.uid()`.
     - `founded_by` is a new nullable `uuid` column with a **unique** index and no foreign key, an attribution like `created_by`. It is null for operator-provisioned organizations. So one account founds at most one organization by shape (AD-3), not by a check.
     - Then insert the Founding Admin, with exactly the domain rows the operator script writes for its admin: role `admin`, the given name and allowance, `email` from `auth.users.email`, and `username` per AD-12.
     - Q6's other end is the RPC's, as it is the script's. No constraint can require an organization to be born with an admin, and the zero-admins triggers fire only on update and delete. So the RPC writes both rows in one transaction or neither.
     - 0052's trigger seeds the annual-leave type. Nothing else is written: no team, shift type, pattern, hour band or setting (FR-97, SM-C3).
  8. **The answer.** `{ "code": "ORGANIZATION_CREATED", "organizationId", "slug" }`. The SPA then calls `refreshSession()`, and the hook stamps the claim. If the refresh fails, `sessionDestination` (AD-24) retries it once before routing. A later call to `create_organization` by an account that already has its row answers `ORGANIZATION_NOT_CREATABLE`, and the SPA treats that answer as "refresh and route", never as an error screen.
  - **Tests.**
    - `test/provisioning.test.ts`: a self-provisioned organization and an operator-provisioned one leave the same set of non-empty tables.
    - The function's ACL.
    - Each refusal, the two returned limits, and the race of two calls from one account (one organization).
    - A self-provisioned fixture organization runs the full `test/rls-isolation.test.ts` (Q29, NFR-30).
  - **Not an AD-16 operation, and not an AD-3 trigger.** It writes as the definer's owner past the insert policies (no policy lets a session insert `organizations`), so its checks are its own, stated here once. `audit_events` records both inserts with the founding account as actor (AD-11).

### AD-24 — Onboarding is a path over shipped surfaces, and it stores nothing it can derive

- **Binds:** CAP-28; FR-96, FR-97; SM-C3; DI-8; UX-DR61
- **Prevents:**
  - a wizard that implements a second write path for a surface that already has one (hour bands, teams, shift types, the rotation, members);
  - a wizard that pre-fills an organization;
  - a stored progress flag that drifts from the rows it describes.
- **Rule (Architect pass 2, 2026-11-21; stories 19.3, 19.4).**
  - **Where a session goes is one function.** `sessionDestination` in `features/auth/services` is listed in `FEATURE_PUBLIC`. The `_app` guard, `/postavljanje`'s guard and the sign-in screen all use it. It takes the session, its claim and AD-12's kind, and answers one of these:
    - a claimed session goes to the app as today, or to steps 2–7 when it asks for `/postavljanje` as an active admin (`/postavljanje/<korak>`), else to *Danas*;
    - a claimless email identity goes to step 1, the create-organization form (AD-23). After `ORGANIZATION_CREATED`, or after `ORGANIZATION_NOT_CREATABLE`, it refreshes the session once and asks again;
    - a claimless username identity is signed out (it has lost its `members` row);
    - a refused sign-in or refresh (`SIGN_IN_REFUSED`: deactivated or suspended) is signed out, with the existing neutral message.
  - **One write path per fact.** Each step is a page that composes the shipped surface's own `components/**` and `hooks/**`, as the module-boundary convention lets a page. Its writes are that surface's own services, under its own snapshot keys and declared dependents (AD-13, *Mutation*). `features/onboarding` holds the rail, the step list and the progress hook, and imports no other feature's `services`.
  - **Progress is derived** (AD-1). Five of the seven steps have a fact, and a step is done when its fact exists:
    - hour bands: at least one;
    - teams: one not archived;
    - shift types: one not archived;
    - the rotation: a rotation assignment exists;
    - members: more than one member.

    Step 1 is done by existing, and step 7 is the end. The progress is **one hook**, `features/onboarding/hooks/use-onboarding-progress.ts`, listed in `FEATURE_PUBLIC`. It reads each fact through its owning feature's own query options, under the key that surface already reads, never a key of its own (AD-13). Those options are added to `FEATURE_PUBLIC` as needed. The rail and the *Danas* card both use the hook, so they cannot disagree. *Preskoči za sada* is navigation, and nothing is stored for it.
  - **What is stored.** Only `organizations.onboarding_dismissed boolean not null default false`. An active admin writes it through `organizations`' existing update policy, with its own column grant.
  - **The *Danas* card** `Postavljanje: još N koraka`, where N is the number of fact steps not done (at most 5). It is drawn for an active admin only, and only when the organization was founded by signup (`founded_by` set), is not dismissed, and has steps left. An operator-provisioned organization never sees it. It is a mark outside *Danas*'s freshness key set, as the loan line is (AD-13, 18.5): drawn when its reads are there, absent while they are not, and never holding the skeleton.
  - **Nothing is pre-filled** (D9, D11).
    - Every step starts empty and nothing is selected.
    - The proposed slug comes from the name the user typed.
    - The timezone is proposed from the browser's resolved zone, shown, and confirmed by the user, so it is the user's own value.
    - The locale is shown read-only.

    Tests: a fresh organization's rows (19.4's acceptance criteria), and a literal sweep of the `signup` and `onboarding` namespaces for fire-department terms, `Dan`/`Noć`, four teams and 12 hours.
  - **Members** are added by admin-issued credentials, the shipped `createUser`. No invitation path exists, and 19.4 builds none (Deferred). UX-DR61's "or invitation" means the shipped credential hand-off. That narrows FR-96's wording, so it is recorded for the founder (F2).
  - **19.4's UX review with mockups** precedes its spec freeze. It covers `/registracija`, `/potvrda`, `/zaboravljena-lozinka`, steps 1–7 at phone and desktop width, the *Danas* card, and the empty states.

### AD-25 — Abandoned accounts are deleted by one job, and only the operator suspends

- **Binds:** CAP-28; FR-101; D-S7 (ratified 2026-11-21); PRD Q12
- **Prevents:** a deletion that reaches an account which has, or is about to get, a `members` row; a second deletion path; suspension as a switch a session can reach.
- **Rule (Architect pass 2, 2026-11-21; story 19.5).**
  - **One job.** pg_cron `housekeeping` runs daily at 03:15 UTC, clear of the 02:30 Europe/Zagreb backup. It calls `private.delete_abandoned_accounts()`, a definer owned by the migration owner that no session role may execute. It selects candidate accounts that have no `members` row and are either:
    - unconfirmed, created more than 7 days ago; or
    - confirmed more than 30 days ago (`email_confirmed_at`).

    It takes each with `for update skip locked`, so an account inside `create_organization` (AD-23, step 1) is skipped. After the lock it checks again that no `members` row exists, then deletes that `auth.users` row, and GoTrue's foreign keys cascade its identities, sessions and tokens. It also deletes `private.organization_attempts` rows older than 30 days. It returns the counts, which `cron.job_run_details` keeps.
  - **What it never deletes.** An account with a `members` row, in any organization and of either kind, is never a candidate. Neither is an organization or a domain row.
  - **Operator scripts** in `supabase/operator/`, SQL over the tailnet as provisioning is (DEPLOY.md §7):
    - `suspend-organization.sql` and `unsuspend-organization.sql` set and clear `organizations.suspended` (AD-10) by slug;
    - `signup-report.sql` is the abuse query: accounts by day and confirmation state, organizations founded per rolling 24 hours against the ceiling, every organization founded by signup (slug, name, created, suspended, member count; FR-101's list), and the accounts with the most attempts. It reads, and writes nothing.
  - **DEPLOY.md** carries the job, the scripts, the runbook, the opening of `signup_settings` on staging, and the D-S5 production-opening checklist (`SECURITY-REVIEW-EPIC-19.md` beside this spine).

## Consistency Conventions

| Concern | Convention |
| --- | --- |
| Naming — database | `snake_case`, plural tables (`leave_records`), singular columns. Every organization-scoped table carries `organization_id` as its first column. |
| Naming — TypeScript | `camelCase` values, `PascalCase` types. Domain terms match `glossary.md` exactly — `ShiftType`, `HourBand`, `RotationAssignment`, `ScheduledShift`, `LeaveDay`. A synonym is a contract violation. |
| Ids | `uuid` primary keys, generated database-side. |
| Dates and times | Dates as `date`. Times as `time` without zone. Durations and clock arithmetic as integer minutes (AD-6). Never a `timestamptz` outside `created_at` and the other attribution instants (`removed_at`, `decided_at`, …, `audit_events.occurred_at`, and `private.organization_attempts.attempted_at`, AD-23). |
| Change history | Every organization-scoped table attaches AD-3's two audit triggers in the migration that creates it, or is named excluded in AD-11; nothing writes `audit_events` but the trigger and 14.1's backfill. |
| Derived-value shape | Plain serializable objects from `packages/domain`. No classes, no getters, no dates-as-objects. |
| Error and warning shape | `{ code, ...operands }` (AD-8). Codes are `SCREAMING_SNAKE`, stable, and translated only at the edge. |
| Refusals vs warnings | A refusal means the state is unrepresentable and is enforced by schema shape (AD-3). Everything else warns and never blocks — except an AD-5 erasure. |
| Snapshot shape | One canonical `OrganizationSnapshot(window)` type. A surface narrows it by selecting fields — it never defines its own shape for the same rows, so two surfaces cannot name the same data differently. |
| Mutation | Writes are direct PostgREST calls invalidating their surface's snapshot key AND every key whose read embeds or derives from the rows they write (AD-13). Those dependents are declared once per write (`features/teams/services/dependents.ts` for team and membership writes) and re-read only after a write that landed; a refusal re-reads only what its own screen reads, and a failed re-read never turns a landed write into a refusal. No optimistic updates for hours, leave balance, or conflict state. |
| Auth context | `organization_id` from the JWT claim; role and active status from the helper (AD-10). Never trust a client-supplied organization or role. |
| Migrations | Files in `supabase/migrations`, forward-only, promoted local → staging → prod. Never edited after promotion. *Amended 2026-11-20 (self-hosting):* applied to a stack by `supabase db push --db-url` (and checked by `supabase migration list --db-url`) over the private tailnet, where Postgres is published from `127.0.0.1` by `tailscale serve`; never through a public Postgres port, never by a container inside the stack. |
| Names | Every name check is `private.name_key(name) <> ''` and every name-uniqueness index is on `private.name_key(name)` (since `0024`): trimmed of one literal white-space class, NFC, lower-cased. A new name column uses the same, never `btrim(name)` or `lower(btrim(name))`. The client mirror is `apps/web/src/utils/name.ts`; `test/supabase-scaffold.test.ts` fails a later migration that goes back to `btrim`. |
| Strings | No literal user-facing text outside `i18n`. Domain and database return codes and values only. |
| Module boundaries | A feature in `apps/web` deep-imports its own modules freely, and another feature's only if that module is listed in `FEATURE_PUBLIC` in `eslint.config.js` (module paths, never folders). A feature never imports app-level code (`pages/`, `router`, `App`, `main`). Every other file under `apps/web/src` may also import any feature's `components/**` and `hooks/**`, but never a bare `@/features/<m>`. A local ESLint rule, `shift/feature-boundaries`, enforces it on the resolved path of every import form, and refuses a specifier with a mid-path `.`/`..`, a `//` or a mis-cased feature; tests, specs, fixtures and `__tests__/` are exempt. There are no `index.ts` barrels (human decision 2026-09-27): they would join seven features into one import cycle. A page composes features and holds no query, mutation or derivation of its own. |

## Deferred

- **Organization-data rank and position lists.** Fire rank and team position are fixed code lists behind the `uses_fire_ranks` setting (PRD FR-18a — a bounded exception to DI-8's spirit, `sprint-change-proposal-2026-09-25.md`). **Revisit when** a second organization needs ranks or positions: the lists become organization rows, the codes migrate to seeded rows, and the setting goes.
- **Multi-organization membership.** Not built; the current non-goal licenses AD-10's claim. **Revisit when** a user genuinely needs two organizations — the claim becomes a set or a per-request selection, and every policy reading it changes together, as one coordinated move.
- **Materialization for scale.** AD-1 holds at the pilot's scale and at Q20's several hundred members. **Revisit when** a surface misses Q17's two-second budget on real data, measured rather than assumed.
- ~~**Conflict-resolution history.**~~ **Resolved 2026-11-16 (Epic 14 Architect pass):** every write to `conflict_resolutions`, a supersession or removal included, is an `audit_events` row from story 14.1 on (AD-11). Resolutions themselves stay current-state rows.
- **Change-history retention and redaction.** `audit_events` is kept without limit (PRD open question 9), and a departed member's personal details stay in its `old_row`/`new_row`. Only the owner, as an operator task, deletes or rewrites an event. **Revisit when** a retention rule or an erasure request is required, or one organization's history passes about a million rows: pruning or redaction then becomes a documented operator job, never a session's privilege.
- **Realtime.** No subscriptions; surfaces refetch. **Revisit when** two admins working the same conflict queue becomes a real scenario rather than a hypothetical.
- **Typed linting.** TypeScript 7 has no stable programmatic API until 7.1. **Revisit at** 7.1, or sooner if typed lint rules are wanted — fallback is pinning TypeScript 5.x, which nothing else in this spine depends on.
- ~~**Shift reminders (needs projection outside the browser).**~~ **Resolved 2026-11-21 (Architect pass 1):** projection runs on the server in `remind` (AD-1 scope note, AD-7, AD-14, AD-18, AD-19). A reminder of an upcoming shift is a fact no request asserts: it would need the schedule projected on the server, which AD-1 and AD-18 keep in the browser. Out of v1. **Revisit when** a reminder is required and a projection outside the browser is accepted as an architecture change.
- **Organization-specific PWA manifest.** The manifest is one static file named "Shift" (human decision 2026-10-19) with the product icon; no organization's name or logo is in it. **Revisit when** an organization wants its own name or logo on the home screen — the manifest then has to be served per organization, which a static build cannot do from one file.
- **Storage-level policy detail** for branding assets beyond Q4's ownership rule. **Revisit when** the upload surface is built.
- **Claim-code identity**, the fully server-free alternative to AD-16: an admin issues a one-time code, the member signs up, and the exchange is an ordinary RLS-governed write linking their auth user to a pre-created member row — an unlinked account reads nothing, so open signup is harmless. Rejected because it reworks CAP-1 and CAP-4. One of its reasons no longer holds: since story 7.8 the member chooses their own password at the first sign-in (the admin-issued one is a one-time, four-word credential), so "moves password choice to the member" is now true of AD-16 as well. The account is still issued by an admin, so CAP-1 and CAP-4 are unchanged. **Revisit if** the AD-16 function ever needs to be removed, or if it starts accreting responsibilities its rule forbids.
- **Dedicated production host** (added 2026-11-20, self-hosting). Staging, production, Coolify and development workloads share one host (decisions H-1, H-14). **Revisit when** a second organization signs, host memory stays above 75 %, or an incident is caused by a non-production workload: production moves to its own VPS, with the same compose file.
- **Point-in-time recovery** (added 2026-11-20, self-hosting). Backups are daily logical dumps to an off-host target (RPO 24 h, decision H-12). **Revisit when** a day of lost writes is no longer acceptable: WAL archiving to the backup target.
- **High availability** (added 2026-11-20, self-hosting). One host is the single point of failure, accepted for the pilot with an off-host backup and a rehearsed restore. **Revisit when** an availability target is contracted.
- **Realtime, analytics and pooler services** (added 2026-11-20, self-hosting). Not deployed in the self-hosted stacks: no subscriptions (see Realtime above), logs read through Coolify, PostgREST pools its own connections. **Revisit when** any of them is needed, together with its memory budget.
- **One reminder assembly per organization** (added 2026-11-21, Architect pass 1). `reminder_inputs` builds AD-19's assembly once per member with reminders on, every 5 minutes, so the organization's configuration repeats for each member. **Revisit when** a `remind` run takes more than 30 seconds (pg_net's call times out at 55 s) or its read passes about 5 MB: one assembly per organization, with the member list beside it.
- **Feed rate limiting** (added 2026-11-21, Architect pass 1; *ratified by the founder 2026-11-21 (D-S1)*). A 256-bit token makes guessing pointless, and each fetch is one indexed lookup and one projection. **Revisit when** feed traffic is measurably a load: Kong's `rate-limiting` plugin on the `calendar-feed` route, which DB-less Kong 2.8 needs added to `KONG_PLUGINS` with `policy: local`.
- **Founder decision F1: the mail routes' timing, if Kong cannot relay** (added 2026-11-21, Architect pass 2). AD-22's primary design answers at once and relays to GoTrue in the background. If 19.1's rehearsal shows that Kong's sandbox cannot run `resty.http` from a timer, the masked answer still waits on GoTrue. A new signup then takes measurably longer than a known address (a password hash plus SMTP), and so does a recovery for a known address. The founder then picks one:
  - accept that timing oracle;
  - move Auth email to GoTrue's send-email hook into `notify`'s outbox, which changes D-S4's mechanism and puts a verification token in an outbox row;
  - open Kong's untrusted Lua more widely.

  **This gates production opening, not staging.**
- **Founder decision F2: FR-96's "or invitation"** (added 2026-11-21, Architect pass 2). AD-24 reads it as the shipped credential hand-off and builds no email invitation. The recommended default is to confirm that reading. The alternative is a new invitation path, which amends AD-12 with a third identity path.
- **Captcha on signup** (added 2026-11-21, Architect pass 2; D-S3 ratified). A captcha means a third-party provider, so none is used. **Revisit when** `signup-report.sql` shows abuse that AD-21's limits do not hold. Cloudflare Turnstile's free tier is then a GoTrue setting plus one widget, and it reopens D-S3.
- **Disposable-address blocklists** (added 2026-11-21, Architect pass 2). A maintained list is a third-party dependency. **Revisit with** the captcha.
- **Changing one's own sign-in address** (added 2026-11-21, Architect pass 2). An email identity keeps the address it signed up with. GoTrue's double confirmation guards a direct call, and no surface offers it. **Revisit when** a Founding Admin needs it: it is a GoTrue email change plus a `members.email` decision. AD-12's predicate is unaffected, because neither kind can become the other.
- **Invitations by email** (added 2026-11-21, Architect pass 2). Members join through admin-issued credentials only (AD-24). **Revisit when** a customer asks: an invitation would be a third identity path and amends AD-12.
- **Onboarding templates by Organization Type** (added 2026-11-21, Architect pass 2, from the v2 proposal). SM-C3 and DI-8 forbid them. **Revisit only** with a second-industry customer and an explicit SM-C3 review.
- **Self-service deletion of an account or an organization** (added 2026-11-21, Architect pass 2). Only the operator deletes or suspends (AD-25). **Revisit when** an erasure request arrives; it then goes with "Change-history retention and redaction".
- **Second factor for email identities** (added 2026-11-21, Architect pass 2). A Founding Admin's account is reachable from the internet with a password alone, as every account is today. **Revisit before** production opens, if the security review (D-S5) asks for it: GoTrue's TOTP needs no new provider.
- **Two-way calendar sync** (added 2026-11-21, Architect pass 1, from the v2 proposal). The feed is read-only by design. **Revisit when** a customer asks to edit shifts from their calendar app, which would be a new write path under AD-9.
